## 4. 仍存在的分歧

以下是我与既有设计/文档之间**未取得一致**的判断，需要评审时明确取舍。不是「我错了」，也不是「文档错了」，而是同一约束下的不同权衡。

| 编号 | 分歧 | 既有立场 | 我的立场 | 理由 |
| --- | --- | --- | --- | --- |
| **G1** | 失败方向是否一律 fail-closed | 规则、上报、证书「一律失败关闭」 | **按语义分级**：完整性（规则内容、远端开关）关闭；可用性（升级闸门、统计上报）开放 | 闸门是运营手段不是安全边界；配置写错时把全量用户打死在 426 上的代价，高于多服务一个旧版本 |
| **G2** | 事件时间用谁的 | 服务端当前时间（现状） | **接受客户端 `ts` 但钳制到 7 天窗口** | 完全信任可被无鉴权端点污染；完全忽略则离线补报必然错日。钳制是唯一可行中间态 |
| **G3** | 幂等实现 | 未实现 | **`epoch + seq` 高水位**，不用内容哈希 | 状态 O(设备数) 而非 O(事件数)；内容哈希会把「连点两次」误判为重复 |
| **G4** | 文档策略 | 持续新增 DESIGN/PLAN 文档承载知识 | **能机检的写成测试，文档只留「为什么」** | 本轮 17 项漂移中 8 项可机检；文档越多，漂移面越大 |
| **G5** | 通用技能与项目规则的优先级 | `software-development-full` 自称「项目规则优先」 | 同意原则，但**优先级声明必须出现在 description 里** | 埋在 1274 行正文的 0.1 节，Agent 大概率读不到，等于没有优先级 |
| **G6** | 门禁的执行方式 | 本地钩子 + CI | 同意，但**钩子必须自动启用且被 CI 校验** | 当前 `core.hooksPath` 靠手工配置，未配置即零保护，而 CI 不知道这件事 |

> **分歧的收敛方式**：G1–G3 属技术判断，建议在 `DESIGN-SERVER-MOBILE-READINESS` 评审时一次定；G4–G6 属流程判断，建议在 `FOLLOW-UP-DOC-AUDIT` 与 `FOLLOW-UP-PROCESS-AUDIT` 处置时定。**不要在实施 PR 里顺手决定。**

## 6. 分阶段实施计划

### 6.0 依赖关系

```text
阶段 0（止血）──┬──> 阶段 1（可信数据）──> 阶段 3（可运营）
                ├──> 阶段 2（可验证）──────┘
                ├──> 阶段 4（可治理，持续）
                ├──> 阶段 5（客户端开箱可用，可与 1/2 并行）
                └──> 阶段 6（合规与分发，最长的关键路径）
```

- 阶段 1 依赖阶段 0 的 `store.ts` 修复（归日改动会触碰同一函数）；
- 阶段 3 依赖阶段 1（压缩要在签名口径确定后做，否则「签压缩字节」的风险无人兜）；
- 阶段 2 与阶段 1 可并行（一个动客户端测试基建，一个动服务端数据路径）；
- 阶段 4 贯穿始终，不阻塞任何阶段；
- **阶段 5 与 1/2 完全独立**（客户端规则库与 UI，不碰服务端数据路径），但**阶段 5 的价值高于 3 和 4**——它决定「装了有没有用」，见 [PLAN-CLIENT-REFORM.md](PLAN-CLIENT-REFORM.md) §2.1；
- **阶段 6 是关键路径**：App 备案审核约 20 工作日，必须在任何「公开分发」动作之前启动，否则会阻塞全部对外发布。

### 阶段 1 — 可信数据（优先级 P0，2 个 PR）

**目标**：统计从「大致对」变成「可解释」。对应 Q1 选 B。

| 步骤 | 内容 | 出口条件 |
| --- | --- | --- |
| 1.1 | `ts` 归日 + 钳制到 7 天窗口 + `STATS_TZ`（默认 `Asia/Shanghai`） | 23:59 事件在 00:01 到达时归前一日；`ts=0`/未来 1 年被钳制 |
| 1.2 | `epoch + seq` 幂等高水位（服务端先接受，旧客户端不发送即空操作） | 重复 seq 只计一次；空洞不推进高水位；epoch 变化后 seq 可重用 |
| 1.3 | 上报载荷加 `appVersion` | `/stats/summary` 可返回版本分布 |

**回滚**：`STATS_EVENT_TIME=off`、`REPORT_IDEMPOTENCY=off` 两个 env 开关，改配置重启即回退。

### 阶段 3 — 可运营（优先级 P1，2 个 PR）

**目标**：让服务端从「能跑」变成「能维护、能换密钥、能看住」。

| 步骤 | 内容 | 出口条件 |
| --- | --- | --- |
| 3.1 | 压缩（gzip，`Bun.gzipSync`）+ 签名口径固化（签未压缩字节）+ `Vary` | 解压后字节与签名原文一致；旧客户端不受影响 |

## 7. 技术方案

### 7.1 整体架构（目标态）

分四层，每层只解决一类问题，跨层只经一个出口。

| 层 | 现状 | 目标 | 关键约束 |
| --- | --- | --- | --- |
| **客户端数据层** | 事件即发，失败即丢 | 待发队列（2000 条 / 7 天，丢最旧）+ 单消费者按序发送 | 队列持久化复用既有 `SecureStore`，不新增存储栈 |
| **传输层** | HTTPS + pin + HMAC，无压缩 | 加 gzip 协商、`Retry-After` 退避、错误分类 | 签名覆盖**未压缩**字节；客户端不得手写 `Accept-Encoding` |
| **服务端契约层** | if-chain 路由，逐 handler 手写限流 | 表驱动路由 + 统一中间件顺序 + 幂等/归日/分页/闸门 | 中间件顺序由表保证，不靠每个 handler 自觉 |
| **存储与观测层** | JSON 分片 + JSONL 日志 | 短期维持 JSON（R2 迁 SQLite）+ 结构化日志固定字段 | 存储接口先收敛，为 R2 铺路但不接管 |

**数据流（事件上行）**：

```text
跳过事件 → 队列(seq++) → 批量≤50 → HTTPS+pin → 限流(IP+device双桶)
        → 幂等(epoch+seq 高水位) → 归日(clamp ts → STATS_TZ 日键)
        → 分片写入(tmp+rename) → 汇总缓存失效
```

**数据流（规则下行）**：

```text
客户端 If-None-Match(hash) → 服务端比对 rules.hash
  → 命中 304（零正文）
  → 未命中 200 + gzip + ETag + X-Rules-Signature
  → 客户端解压 → HMAC 验签 → 失败关闭拒载
```

### 7.2 核心技术选型

| 决策 | 选择 | 放弃的方案 | 理由 |
| --- | --- | --- | --- |
| 幂等状态 | 内存 `Map<deviceId:epoch, lastSeq>`，50k 上限 + 24h TTL | Redis / 落盘 | 零依赖；重启窗口重复量级极小；R2 后可换 SQLite 表 |
| 事件时间 | 客户端 `ts` + 7 天钳制 | 服务端时间 / 完全信任 | 见 G2 |
| 压缩 | `Bun.gzipSync` | 引入 `compression` 中间件 | Bun 内置，零运行时依赖 |
| 时区 | `Intl.DateTimeFormat` + IANA 名 | 固定 +8 偏移 | 固定偏移在 DST 地区错一小时；Bun 内置 ICU |
| 覆盖率 | kover（Gradle 原生） | jacoco 手写配置 | 零额外依赖，与现有 build-logic 契合 |
| 路由 | 声明式 `Route[]` 表 | 继续 if-chain | 让「限流先于鉴权」成为表的性质而非每个 handler 的纪律 |
| 契约守卫 | 双端共享 JSON 夹具 | 文档对账 | 沿用 `selectors.contract.json` 已有先例，成本最低 |
| 可观测 | 结构化日志固定字段 → 后续 `/metrics` | 立即上 OpenTelemetry | 单实例上 APM 是过度工程；先让字段稳定 |

### 7.3 关键模块设计

**M1 上报可靠性**（阶段 1）

- 队列：环形缓冲，容量 2000 / 时限 7 天，溢出丢最旧；出队条件 = 2xx 且 `ok===true`。
- 错误分类：`2xx` 出队；`400/413/415/422` **出队**（毒丸，否则卡死整队）；`401/403` 出队并标记配置错误；`408/429/5xx/网络` 保留并退避。
- 幂等：`(deviceId, epoch)` 为身份，`seq` 单调；`seq<=lastSeq` 丢弃，`seq===lastSeq+1` 推进，`seq>lastSeq+1` 接受但不推进（空洞合法）。
- 归日：`clamp(ts, now-7d, now+5min)`，日键经 `STATS_TZ` 求值，只允许写保留窗口内分片。

**M2 传输层**（阶段 3）

- 压缩仅对 `application/json` 且 >1 KiB；`Vary: Accept-Encoding`；ETag 基于未压缩 body。
- 退避：`min(base×2^attempt, 15min) × (0.5+rand×0.5)`，`Retry-After` 作下界。
- 分页：`summary?limit=50`（上限 200）+ `appsTotal`；全量走 admin-only `/stats/apps`。

**M3 配置与生命周期**（阶段 4）

- `GET /api/v1/config` 与规则同密钥同签名头；客户端同样失败关闭。
- 版本闸门：`X-Client-Version-Code` 缺失即放行（失败开放，见 G1）；软段返回 `upgradeHint`，硬段返回 426。

**M4 可观测**（阶段 4）

- 日志固定字段：`duplicates` / `gaps` / `clamped` / `rate_limited` / `queue_depth`。
- 指标三类：请求量（按路由/状态）、限频命中、规则条数与版本。

**M5 契约守卫**（阶段 4）

- `ApiDocContractTest`：`API.md` 中的 `SCREAMING_CASE` 必须在 `config.ts` 的 `process.env.*` 集合内。
- `DocsPathContractTest`：文档中被反引号包裹的仓库路径必须存在（豁免 `▲` 行）。
- `BrandContractTest`：`docs/**/*.md` 的 H1 与 `rootProject.name` 不得含 `LEGACY_BRAND`。

### 7.4 数据模型变更

| 对象 | 变更 | 兼容性 |
| --- | --- | --- |
| 上报事件 | 新增 `seq`（number）、`appVersion`（string，可选） | 纯增量；旧客户端不传即走现状路径 |
| 上报批次 | 新增 `epoch`（string 8–64） | 同上 |
| 统计分片 | `byApp` 不变；`events[]` 增加 `eventTs`（客户端时间）与 `serverTs` | 新增字段，旧数据读取时缺省回填 |
| 汇总响应 | 新增 `appsTotal`、`duplicates`、`gaps`、`clamped` | 纯增量 |
| 配置响应 | 新增端点 `{schemaVersion, configVersion, flags}` | 新端点，无兼容问题 |

### 7.5 风险与应对

| # | 风险 | 概率 | 影响 | 应对 | 触发信号 |
| --- | --- | --- | --- | --- | --- |
| R1 | 压缩开启后签名失配，导致**全量客户端拒载规则** | 中 | 极高 | 签名口径写进代码注释 + API.md + 契约测试三方固化；灰度按 env 开关 | 客户端日志出现 `signature mismatch` 集中上升 |
| R2 | 客户端手写 `Accept-Encoding` 导致 OkHttp 不自动解压 | 中 | 高 | 客户端加断言：禁止在 `Request.Builder` 设该头 | 解压异常 / 验签失败 |
| R3 | 幂等状态重启丢失导致重复计数 | 高 | 低 | 接受；以 `duplicates` 指标观测 | 重启后 `duplicates` 突增 |
| R4 | 归日钳制让超 7 天离线数据落到到达日 | 中 | 中 | 文档明示；队列上限同为 7 天，二者一致 | `clamped` 计数 |
| R5 | 密钥轮换中断导致规则停更 | 低 | 极高 | 双签过渡 + 观察一个版本再移除旧钥 | `rules_signing_key_missing` 告警 |

| R7 | 硬闸门配置错误导致全量 426 | 低 | 极高 | 默认关闭；缺头放行；上线前用 admin 端点试算受影响版本 | 426 比例突增 |
| R8 | SQLite 迁移（R2）与本文改动冲突 | 中 | 中 | 存储接口先行收敛；协议变更与存储迁移分 PR | 迁移 PR 需同时改协议 |

## 9. 不做的事

| 不做 | 理由 |
| --- | --- |
| 引入 Redis / Postgres / 消息队列 | 违背零运行时依赖；R2 的 SQLite 已足够 |
| 用户账号体系 | 工具类 App 的零账号体验是产品前提 |
| 立即上 OpenTelemetry | 单实例阶段是过度工程；先把日志字段稳定 |
| 重写路由层之外的大规模重构 | 现有 97 + 287 例测试是资产，重构应小步 |
| 为每份文档加「最后更新时间」靠人工保鲜 | 时间戳不产生正确性 |
| 一次性硬闸门淘汰旧客户端 | 长尾用户直接断供，且无数据支撑阈值 |
