## 1. 结论摘要

服务端的**安全底线**（TLS 强制、HMAC 失败关闭、证书固定、载荷上限）已经超前于它的规模，但**移动端语义**落后于它的规模。差距集中在三处：上报不可靠、传输不经济、生命周期无协商。

| 级别 | 问题 | 现状证据 | 后果 | 章节 |
| --- | --- | --- | --- | --- |
| **P0** | 上报无待发队列 | `SyncClient.kt:254-289` 失败即静默丢弃 | 断网/Doze 期间事件永久丢失，统计系统性偏低 | §5.1 A1 |
| **P0** | 无幂等键 | `store.ts:267` 直接 `count += 1` | 「已处理但响应丢失」重试双计 | §5.1 A2 |
| **P0** | 事件 `ts` 被丢弃 | `store.ts:268` 用 `getDayKey()` | 补报事件全算到补报当天，`byDay` 曲线失真 | §5.1 A3 |
| **P1** | 无响应压缩 | 全仓无 `Content-Encoding` | 规则包可达数百 KB，4G 白付流量 | §5.2 B1 |
| **P1** | 429 无 `Retry-After` | `errorJson(429, ...)` 无头 | 客户端盲猜退避，易形成重试风暴 | §5.2 B2 |
| **P1** | 汇总无分页 | `statsSummary()` 全量拉平 `byApp` | 最坏 90 天 × 2000 条一次性返回 | §5.2 B3 |
| **P2** | 无最低版本闸门 | 只有 `SCHEMA_VERSION_MIN` | 无法淘汰有缺陷的旧客户端 | §5.3 C1 |
| **P2** | 无远端开关 | 规则出问题只能改 `rules.json` 或发版 | 缺 kill switch | §5.3 C2 |
| **D** | 路由/安全头/配置三处可维护性债 | 见 §2.2 R4–R6 | 改动面扩大后必然踩坑 | §5.4 |

**一句话判断**：P0 三项补齐后，这套后端才从「能跑的服务」变成「可信的移动端数据管道」；P1 决定它在弱网国家的可用性；P2 决定它能否长期运营。

## 3. 目标与非目标

### 3.1 目标

1. **不丢**：设备在合理离线窗口内（默认 7 天 / 2000 条）产生的跳过事件，网络恢复后**至少一次**送达。
2. **不重**：同一事件在任意重试次数下只计一次（服务端幂等）。
3. **不错日**：事件归入**事件发生日**（按配置时区），而非到达日。
4. **省流量**：规则下行与统计上行的字节数在弱网下可接受；限流可被客户端正确解读。
5. **可淘汰**：能以「软提示 → 硬闸门」两段式淘汰有缺陷的客户端版本。
6. **可维护**：新增一个端点/配置项/安全策略只需改一处，且被机器守护。

### 3.2 非目标

| 不做 | 理由 |
| --- | --- |
| 引入 Redis / Postgres / 消息队列 | 违背零运行时依赖与单实例定位；R2 的 SQLite 已能覆盖到万级 QPS 之前 |
| 用户账号体系与设备令牌鉴权 | 工具类 App 的零账号体验是产品前提；统计不是安全关键路径，见 §11 |
| 推送通道（FCM / 厂商通道） | 当前无「服务端主动触达」的产品需求；接入成本（隐私合规 + 国内厂商适配）远大于收益 |
| 把 `rules` 与 `config` 合并成单一 bundle | 见 §11 取舍 3 |
| 多实例水平扩展 | 需先完成 R2；本文只保证「不阻碍」而非「已支持」 |

## 4. 设计原则

1. **协议增量，语义不破**：所有新增字段对旧客户端**不可见且无害**；旧路径行为逐字节不变。移动端无法强制升级，任何 breaking change 的代价都是用户流失。
2. **失败方向按语义选，不一律 fail-closed**：**完整性**（规则内容、远端开关）失败关闭——被篡改比不可用更糟；**可用性**（升级闸门、统计上报）失败开放——不可用比不精确更糟。这条区分是本文与既有「一律 fail-closed」倾向的关键分歧，理由见 §7。
3. **状态尽量 O(设备数)，不 O(事件数)**：幂等、限流、去重都必须随设备数线性增长，不能随事件数增长，否则长期运行必然被内存打败。
4. **机器可验证优先于文档正确**：凡是双端必须一致的契约，先落成夹具再写实现（沿用 `selectors.contract.json` 的既有先例）。

## 5. 设计方案

### 5.1 A 组：上报可靠性

#### A1 客户端待发队列（协议约束，实现留给 PLAN-OFFLINE-SYNC）

本文只约束服务端**依赖**的那部分行为，避免两处各写一套：

| 约束 | 值 | 理由 |
| --- | --- | --- |
| 队列容量 | 2000 条 / 7 天，**丢最旧** | 移动端磁盘与用户耐心都有限；丢最旧保证近期数据优先，且不会因长期离线无限膨胀 |
| 出队时机 | 收到 2xx **且** 响应体 `ok === true` | 只认应用层确认，不认 TCP 成功 |
| 批大小 | ≤50（与 `MAX_BATCH_EVENTS` 对齐） | 减少 RTT，同时避免单请求超时拖累整队 |
| 触发 | 网络可用回调 + 周期任务 + 手动同步，三路统一入队消费（单消费者） | 多消费者会打乱 seq 顺序，破坏 §5.1 A2 的高水位假设 |
| 持久化 | 与规则缓存同一加密存储 | 复用既有 `SecureStore`，不新增存储栈 |

#### A2 幂等：`epoch` + `seq` 高水位

**协议**（`POST /api/v1/reports/batch`，纯增量）：

```json
{
  "deviceId": "≥8 字符",
  "epoch": "安装期随机 UUID，8–64 字符",
  "events": [
    { "seq": 1024, "pkg": "com.x", "label": "X", "channel": "text", "ts": 1730000000000 }
  ]
}
```

**服务端**：维护 `Map<"${deviceId}:${epoch}", lastSeq>`，容量 50 000、24h TTL（与限流桶同构的 LRU + 定时回收）。

| 情形 | 处理 |
| --- | --- |
| `seq <= lastSeq` | 丢弃，计入响应 `duplicates` |
| `seq === lastSeq + 1`（连续） | 接受，`lastSeq = seq` |
| `seq > lastSeq + 1`（有空洞） | **接受但不推进高水位**——队列丢最旧会产生合法空洞，把它当异常会误杀正常数据；只上报 `gaps` 计数供观测 |
| 缺 `seq`/`epoch`（旧客户端） | 走现状路径，无幂等，响应字段保持 `{ok, accepted}` |

响应：`{ "ok": true, "accepted": N, "duplicates": D, "gaps": G }`。

**为什么不用「内容哈希 + 时间窗去重」**：哈希集合大小随事件量增长（与原则 3 冲突）；且用户连点两次「跳过」会产生同 pkg、同 channel、毫秒级相邻的**真实**两次事件，内容哈希会把它们误判为重复。

**为什么 epoch 不可省**：设备重装后 `seq` 从 1 重新开始，而服务端高水位仍在旧值 → 新装设备的全部事件被判为重复。epoch 让「重装」变成一次干净的身份切换。

**边界**：epoch 变化时不删除旧条目（可能仍在 TTL 内被并发请求引用），仅新建水位；旧条目按 TTL 自然回收。

#### A3 事件时间归日 + 钳制

**现状问题**：`recordSkip` 用服务端当前时间分片，客户端 `ts` 被 `cleanReportEvent` 解析后丢弃。

**方案**：

1. `recordSkip(pkg, label, channel, eventTs)` 增加事件时间参数；`ts` 缺失时回退 `Date.now()`。
2. **钳制**：`clamp(eventTs, now - 7d, now + 5min)`。越界即用 `now` 并计入 `clamped` 计数。
3. **分片键**由钳制后的 `eventTs` 决定；且只允许落在 `[today - STATS_RETENTION_DAYS, today]` 区间——防止伪造 ts 造出海量日分片（一个请求最多碰 8 个日键）。
4. **时区**：新增 `STATS_TZ`（IANA 名，默认 `Asia/Shanghai`），日键经 `Intl.DateTimeFormat(STATS_TZ)` 求值。Bun 内置 ICU，零依赖。

**为什么必须钳制**：上报端点**无鉴权**，客户端自报的时间不可信。不钳制 = 任何人都能把任意日期的统计灌成任意值，且能无限制造日分片文件（磁盘 DoS）。钳制把「可信度」换成了「7 天窗口内的准确性」——这个交换是划算的，因为离线队列上限本来就是 7 天。

**为什么用 IANA 时区而不是固定偏移**：固定偏移在 DST 地区会错一小时；且「今天」是产品语义，必须跟部署地一致，写死在代码里等于把运维约束藏进源码。

#### A4 错误分类：毒丸必须出队

队列最怕的不是失败，是**永久失败**——一条 400 的坏事件会卡住整队，后续全部无法送达。

| 响应 | 队列动作 | 理由 |
| --- | --- | --- |
| 2xx | 出队 | 成功 |
| 400 / 413 / 415 / 422 | **出队** + 本地丢弃计数 | 载荷非法，重试必然再失败（毒丸） |
| 401 / 403 | **出队** + 标记「配置错误需用户处理」 | 重试无意义，且要避免无限打服务端 |
| 408 / 429 / 5xx / 网络异常 | 保留，退避重试 | 瞬时故障 |
| 304 | 不适用（上报无 ETag） | — |

### 5.2 B 组：传输效率

#### B1 响应压缩（与签名/ETag 的交互是重点）

**做法**：对 `Content-Type: application/json` 且 body > 1 KiB 的响应启用 `gzip`（`Bun.gzipSync`，内置零依赖）；同时设 `Vary: Accept-Encoding`。

**三条必须写进代码注释与 API.md 的约束**：

1. **签名口径不变**：HMAC 仍对**未压缩的 JSON 字节**签发，客户端**解压后**验签。若有人「顺手」改成签压缩字节，客户端解压后必然失配，且失配表现为「全量客户端拒载规则」——事故等级最高。
2. **ETag 基于未压缩 body**（沿用现状 `rules.hash`），压缩不改变缓存语义。
3. **客户端不得手写 `Accept-Encoding`**：OkHttp 只有在**自己添加**该头时才自动解压；一旦应用层手写了这个头，`body.string()` 会返回压缩字节，验签必然失败。这是本方案最容易踩的坑，必须进边界矩阵与客户端测试。

**收益**：规则包 JSON 压缩率通常 5–8 倍；统计汇总同理。

#### B2 `Retry-After` 与退避契约

- 429 响应加 `Retry-After: <秒>`，值 = 令牌桶回填 1 个令牌所需秒数 `ceil(60 / capacity)`（读 0.5s、写 6s、上报 2s）。
- 客户端退避：`delay = min(base × 2^attempt, 15min) × (0.5 + random×0.5)`，`Retry-After` 存在时以其为下界。
- 抖动是必须的：否则重启后所有客户端同一秒重试，形成自造的惊群。

#### B3 汇总分页

**现状**：`statsSummary()` 返回全量 `byApp`，`byDay` 限 14 天、`recent` 限 50 条——后两者有界，只有 `byApp` 无界。

**方案**：

- `GET /api/v1/stats/summary?limit=50`（默认 50，上限 200），响应增加 `appsTotal`（总条目数，用于「还有更多」判断）。
- 新增 `GET /api/v1/stats/apps?limit=&cursor=`（**admin 鉴权**）供管理页取全量，游标为 `pkg`（稳定且天然有序）。
- 为什么不让 summary 也支持游标：移动端汇总只需要「头部 + 总量」，多一次 RTT 换完整列表不划算；管理页是桌面浏览器，多一次请求无感。

#### B4 静态资源缓存

`/download` 加 `Cache-Control: no-store`（APK 会变，不能缓存）；`/admin` 加 `Cache-Control: no-cache`（每次校验）；落地页 `/` 因注入版本号，加 `no-cache` + `ETag`（版本号变化即失效）。

### 5.3 C 组：生命周期协商

#### C1 版本闸门（软 → 硬两段式）

- 请求头：`X-Client-Version-Code: <versionCode>`（用 versionCode 而非 versionName，因为它是**单调整数**，比较无歧义）。
- **软段**：规则响应体增加 `upgradeHint: { minVersionCode, downloadUrl, message }`（纯增量字段）。客户端展示可关闭提示。
- **硬段**：`versionCode < HARD_MIN_VERSION_CODE` 时返回 `426 Upgrade Required` + `{ error: "upgrade_required", minVersionCode, downloadUrl }`。
- **缺头 = 放行**（失败开放）。理由：这是运营手段，不是安全边界；配置写错时宁可多服务一个旧版本，也不能把全量用户打死在 426 上。

**为什么必须两段**：一次性硬闸门等于把长尾用户直接断供。软段跑满一个版本周期后，才有数据判断硬闸门的阈值该定在哪。

#### C2 远端配置（同签名，独立端点）

- `GET /api/v1/config` → `{ schemaVersion, configVersion, flags: { ... } }`，与规则**同一 HMAC 密钥、同一签名头**，客户端同样失败关闭。
- 客户端缓存策略与规则一致（ETag + 304）。
- **必须签名**：kill switch 若不签名，中间人可以把「关闭某危险能力」翻成「开启」，这是比篡改规则更直接的攻击面。
- 端点独立而非并入规则包：见 §11 取舍 3。

### 5.4 D 组：可维护性

#### D1 路由表化

现状 `api/index.ts` 是 61 行 if-chain，且「限流先于鉴权」这条安全约定靠每个 handler **手工复制**（`rulesApi.ts:72-75`、`statsApi.ts:9-15` 各写一遍）。漏写一处就是漏洞。

```ts
type Route = {
  method: "GET" | "POST" | "PUT";
  path: string;
  handler: Handler;
  auth?: "admin";              // 显式声明，缺省即公开
  limit?: "read" | "write" | "report";
  body?: boolean;              // 是否需要读体（决定是否做预检）
};
const ROUTES: Route[] = [ /* … */ ];
```

收益：中间件顺序由**表驱动统一执行**（限流 → 鉴权 → 读体 → 处理），不再依赖每个 handler 自觉；并可直接写测试断言「所有写方法的路由要么有 `auth`，要么显式标注 `public: true`」。

#### D2 安全头收敛为单一实现

删除 `server.ts:52-75` 的重复定义，保留 `httpUtil.ts` 一份并补齐缺失指令（`base-uri` / `form-action` / `connect-src`）；`server.ts` 只调用。同时删除死代码 `htmlResponse`、`checkAdminAuth`（R7）。

#### D3 配置集中校验

启动时统一解析 + 校验，失败**快速退出**并打印可读原因（`PORT must be an integer in 1..65535, got "abc"`）。当前 `NaN` 会在 `Bun.serve` 深处炸掉，堆栈不指向配置。

#### D4 契约夹具扩展到响应形状

沿用 `server/test/fixtures/selectors.contract.json` 的双端消费模式，新增 `api.contract.json`：每个端点的必填字段、类型、可选字段、状态码。双端测试消费同一份夹具。

这是**根治 R6 这类文档漂移**的手段——文档可以写错，夹具不会。文档只负责解释「为什么」，夹具负责保证「是什么」。

#### D5 签名密钥轮换（当前最严重的运营单点）

- `RULES_SIGNING_KEY` → `RULES_SIGNING_KEYS`（逗号分隔，**第一个为当前签发密钥**，其余为可接受的旧密钥）。
- 响应同时下发 `X-Rules-Signature`（当前密钥签）与 `X-Rules-Signature-Prev`（旧密钥签同一 body，仅在过渡期存在）。
- 客户端：任一头验签通过即接受。
- 过渡流程：双签上线 → 等一个版本周期（旧客户端升级到能识别 `-Prev`）→ 移除旧密钥。
- **代价**：多一次 HMAC（微秒级）+ 一个响应头。**不做的代价**：换密钥 = 全体客户端规则停更，且因为是 fail-closed，停更对用户是不可见的。

## 6. 边界情况矩阵

| # | 场景 | 期望行为 | 当前行为 | 风险 |
| --- | --- | --- | --- | --- |
| 1 | 离线 7 天，队列溢出 | 丢最旧，保留最近 2000 条 | 全部丢失 | 数据完整性 |
| 2 | 请求已到达、响应丢失 | seq 去重，`duplicates` +1 | 双计 | 统计虚高 |
| 3 | 设备重装 | epoch 变化，高水位重置 | 新事件被判重复（若只做 seq） | 数据丢失 |
| 4 | 客户端时钟错 1 年 | 钳制到 7 天窗口 | 按服务端时间，无影响 | — |
| 5 | 伪造 ts 造 90 天分片 | 只允许写保留窗口，单请求最多碰 8 个日键 | 当前忽略 ts，但改后必须钳制 | 磁盘 DoS |
| 6 | 23:59 上报、00:01 到达 | 归 23:59 那一天 | 归到达日 | 曲线失真 |
| 7 | 零点后长时间无上报 | 汇总缓存需按日键失效 | **返回昨日 `today`**（R1） | 看板错误 |
| 8 | 队列混入非法包名 | 400 → 毒丸出队 | 无限重试 | 队列卡死 |
| 9 | 429 | `Retry-After` + 抖动退避 | 盲猜 | 重试风暴 |
| 10 | 服务端重启 | 限流清零、幂等水位丢失 | — | 重启窗口内可能重复（可接受，见 §7-4） |
| 11 | 签名密钥轮换 | 双签过渡 | **全体停更**（R3） | 运营事故 |

| 18 | 并发上报同日分片 | 单进程同步写，天然串行 | 正常 | 多实例后失效 |

## 7. 关键取舍

| # | 决策点 | 选择 | 放弃的方案 | 理由 | 代价 |
| --- | --- | --- | --- | --- | --- |
| 1 | 幂等实现 | `epoch + seq` 高水位（O(设备数)） | 内容哈希去重（O(事件数)） | 状态随设备数线性增长，长期运行不膨胀；且不会误杀「连点两次」的真实事件 | 需要客户端持久化单调计数器；要求单消费者按序发送 |
| 2 | 事件时间 | 接受客户端 `ts` 并钳制到 7 天窗口 | 完全信任 `ts` / 完全忽略 `ts` | 信任 = 可被无鉴权端点任意污染；忽略 = 离线补报必然错日。钳制取中间态 | 超出窗口的离线数据归到到达日（7 天外本就是极端场景） |
| 3 | 配置端点 | 独立 `/api/v1/config`，复用签名中间件 | 并入 `/rules/latest` 成单一 bundle | 合并后任一方变更都会让客户端全量重载规则；且运营开关与规则内容变更频率差一个数量级 | 多一次 RTT（可与规则同步并发发起） |
| 4 | 重启后幂等状态 | 内存态，重启丢失 | 落盘到分片文件 | 落盘写放大显著，而重启窗口的重复量级极小（秒级、单实例） | 重启后可能少量重复，观测上以 `duplicates` 计数可发现 |
| 5 | 升级闸门失败方向 | 失败**开放**（缺头放行） | 失败关闭（缺头即 426） | 闸门是运营手段不是安全边界；配置错误时宁可多服务旧版本 | 攻击者可省略头绕过闸门（无收益，闸门不保护任何资源） |
| 6 | 压缩与签名 | 签名覆盖未压缩字节 | 签名覆盖压缩后字节 | 压缩率随内容变化，签压缩字节会让签名与内容语义脱钩；且客户端解压后无法验签 | 必须在代码与文档中双重固化「签名口径」，否则后人易改错 |
| 7 | 分页位置 | `summary` 加 `limit`，全量走独立 admin 端点 | summary 支持游标 | 移动端汇总只要头部 + 总量，多 RTT 不划算；桌面管理页多一次请求无感 | 两个端点有部分重复逻辑（用共享查询函数消除） |
| 8 | 路由重构时机 | 在 P0 之后、P1 之前 | 先重构再加功能 | 重构会触碰全部端点，先用 P0 的测试把行为钉住，再重构才安全 | P0 阶段仍需忍受 if-chain 的重复 |
| 9 | 时区 | `STATS_TZ` 可配（IANA），默认 `Asia/Shanghai` | 固定 UTC / 固定 +8 偏移 | UTC 与用户直觉错位；固定偏移在 DST 地区错一小时 | 多一个配置项，且日键计算依赖 ICU（Bun 内置，无新增依赖） |
| 10 | 队列溢出策略 | 丢最旧 | 丢最新 / 拒收新事件 | 近期数据价值更高；且拒收会让「离线越久越无法上报」形成死锁 | 长期离线用户的早期数据丢失 |

## 8. 兼容与灰度

| 变更 | 兼容性 | 灰度手段 |
| --- | --- | --- |
| `ts` 归日 + 钳制 | 协议无变化（字段早已存在） | `STATS_EVENT_TIME=off` 回退到服务端时间 |
| `seq`/`epoch` 幂等 | 纯增量字段；旧客户端无幂等 | `REPORT_IDEMPOTENCY=off` 回退 |
| 响应新增 `duplicates`/`gaps` | 纯增量字段 | 无需灰度 |
| gzip | 依 `Accept-Encoding` 协商，旧客户端不受影响 | 按 `COMPRESSION=off` 回退 |
| `Retry-After` | 旧客户端忽略未知头 | 无需灰度 |
| `limit`/`appsTotal` | 默认值等于「当前行为的上限」，字段纯增量 | 无需灰度 |
| 版本闸门 | 软段纯增量；硬段默认关闭 | `HARD_MIN_VERSION_CODE=0` 即关闭 |
| 路由表重构 | 对外零变化 | 由既有 97 项测试 + 新增路由表测试保护 |
| 双签密钥 | 旧客户端只读 `X-Rules-Signature`，不受影响 | 过渡期后移除旧密钥 |

**统一的回退原则**：每个 P0/P1 能力都配一个环境变量开关，默认值等于「新行为」，出问题时改 env 重启即回退到旧语义，不需要回滚代码。

## 10. 落地顺序与回滚

```
批次 0（纯服务端修复，无协议变更，可独立合入）
  R1 汇总缓存跨天失效 → R2 时区日键 → R4 安全头收敛 → R5 配置校验 → R7 死代码 → R6 文档同步
批次 1（P0，服务端先行，客户端随后）
  A3 ts 归日 + 钳制（服务端单侧即可生效）
  A2 幂等（服务端先接受 seq 但无客户端发送 = 空操作，再上客户端）
  A1 队列（纯客户端，依赖 A2 已上线）
批次 2（P1）
  B2 Retry-After（最小改动）→ B1 压缩 → B3 分页 → B4 静态缓存头
批次 3（P2）
  C1 软段 → C2 配置端点 → 观察一个版本周期 → C1 硬段
批次 4（D 组剩余）
  D1 路由表（在批次 1 的测试保护下重构）→ D4 契约夹具 → D5 双签
```

**为什么批次 0 在最前**：全部是零协议风险的修复，收益立刻可见（看板不再显示错误日期、运维能看到明确启动错误），且不阻塞任何后续工作。

**为什么 A3 早于 A2**：A3 只改服务端，单侧生效；A2 需要双端配合，链路更长。先把「不需要协商就能拿到收益」的部分拿掉。

**回滚点**：每个批次都是独立 PR，回滚 = revert 单个 PR；运行期回滚 = 对应 env 开关置 `off` 重启。

## 11. 未采纳方案及理由

| 方案 | 不采纳理由 |
| --- | --- |
| 上报端点要求设备令牌鉴权 | 需引入注册流程，破坏零账号体验；统计不是安全关键路径，伪造统计的危害上限是「看板数字失真」，用限流 + 条数上限已足够 |
| 引入 Redis 做限流与幂等 | 违背零运行时依赖；单实例下内存实现已满足，R2 后可用 SQLite 表替代 |
| 用 `bun:sqlite` 立刻替换 JSON 分片 | 属 R2 范围，本文只要求存储接口先行收敛（§5.4 D3），避免在迁移时被迫同时改协议 |
| 队列持久化到独立文件（而非加密存储） | 引入第二套存储栈与迁移逻辑；事件本身是低敏感度数据，复用既有 `SecureStore` 足够 |
| 服务端做「事件去重窗口」而不依赖客户端 seq | 无鉴权端点无法区分「重试」与「真实重复」，服务端单侧去重必然误判 |
| 一次性硬闸门淘汰旧客户端 | 长尾用户直接断供，且无数据支撑阈值；必须两段式 |
| 在规则响应里内联所有远端开关 | 变更频率差一个数量级，耦合会导致规则全量重载（见 §7-3） |
