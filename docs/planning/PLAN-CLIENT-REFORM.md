## 1. 结论摘要

三条结论，按重要性排列。

**结论一：客户端的工程化水平显著高于它的功能完成度。**

架构分层（`engine` / `data` / `net` / `service` / `device` / `ui`）、契约测试（`UiContractTest` / `ManifestContractTest` / `ColorSchemeContractTest` 等 10 个 arch 测试）、发布链路（`apksigner verify` + SHA-256 + annotated tag）都达到了可以长期维护的水准。但这些保障的是「改坏会被发现」，不是「用户装了有用」。

真正的断点是一处：**客户端首次启动时规则库为空，核心功能对普通用户等于不存在**（证据见 §2.1）。引导页承诺「智能识别广告内容」，实际行为是什么都不点。

**结论二：合规有三项硬缺口，且风险随能力层级陡增。**

| 缺口 | 性质 | 不处理的后果 |
| --- | --- | --- |
| App 备案 | **法定强制**（工信部信管〔2023〕105 号） | 项目有联网能力（规则同步 / 统计上报），属互联网信息服务；不上架应用商店**不免除**备案义务 |
| 隐私政策 | 法定要求（《个人信息保护法》告知同意） | 当前全仓无隐私政策；已上报 `deviceId` 与跳过记录 |
| 无障碍用途说明 | 平台与舆论风险 | 「非无障碍目的使用无障碍服务」是灰色地带；Google Play 明令禁止（出海路径直接封死） |

反不正当竞争风险与能力层级正相关：L1（只点已有按钮）风险可控，L2（DNS 拦截）性质变化，L3（Hook）风险最高。这也是 [DESIGN-ADS-FILTERING.md](DESIGN-ADS-FILTERING.md) 把 L2/L3 卡在 Phase 0 的正确理由。

**结论三：当前不是面向大众用户的产品，是「技术型用户自建自用」的工具。**

功能方向（自动跳过开屏广告）符合大众真实痛点，但交付形态与大众使用场景错配三处：规则库空、需自建服务器、需手动配置 HMAC 密钥与证书 pin。竞品 GKD 用社区订阅规则解决了这三处，因此本项目在「大众可用」这条赛道上当前没有位置。

**一句话判断**：这份代码值得继续投入，但必须先把「开箱即用」补上，否则工程化投入无法转化为任何用户价值。

### 2.1 决定性证据：开箱即用是断的

| 环节 | 现状 | 证据 |
| --- | --- | --- |

## 3. 第一部分：客户端改造计划

### 3.1 模块范围

按 `client/app/src/main/java/com/qingqi/adskip/` 的现有分层列出改造点。「改什么」一栏只写行为变化，不写实现细节。

| 模块 | 现状职责 | 改造内容 | 改动量 |
| --- | --- | --- | --- |
| `data/` | 规则 / 设置 / 统计的存储与仓库 | **新增内置默认规则集**（首次启动写入）；新增订阅源模型；`RulesRepository` 增加「规则来源」维度（内置 / 订阅 / 手动） | 大 |
| `engine/` | 三通道匹配 + 安全护栏 | 不改匹配逻辑；新增「规则集为空」的可观测信号（供 UI 提示） | 小 |
| `net/` | 规则同步 + 上报 | 服务器配置降为**可选**；新增免密钥的公开规则订阅拉取路径（签名验证保留，密钥随订阅源下发） | 中 |
| `ui/` | 六屏表现层 | 修复 §3.2 批次 2 列出的 P0/P1 项；新增「规则为空」空态与一键导入入口 | 中 |
| `service/` | 无障碍薄编排层 | 不改。稳定，无改造必要 | 无 |
| `device/` | 权限 / 保活 / 磁贴 | 权限引导改为「按当前缺失项逐步引导」，而非一次性列出全部 | 小 |
| `core/` | 加密存储 / 时钟 / 日志环 | 不改 | 无 |
| `server/seed/` | 种子规则 | 从空 `packages` 扩到 Top 30 常见应用的选择器规则（M1d 的实际内容） | 大 |

**范围外**（明确不做，避免范围蔓延）：L2 DNS、L3 Hook、多模块化拆分、服务端存储迁移。前两项受 Phase 0 合规闸门约束，后两项由各自 DESIGN 文档接管。

### 3.3 优先级排序依据

排序用的不是「工作量」也不是「技术难度」，而是**用户价值衰减速度**：

| 批次 | 排序理由 |
| --- | --- |
| 0 | 备案周期最长（20 工作日），且 0.2 决定上报合法性；晚做会阻塞后续所有联网能力 |
| 1 | 直接决定「装了有没有用」。这一环不通，批次 2 的打磨全部无意义 |
| 2 | 影响留存与口碑，但不影响「能不能用」。可在批次 1 之后并行 |
| 3 | 扩大覆盖面，属增量价值 |
| 4 | 风险性质变化，必须先过合规 |

反过来说：批次 2 的 P0 项（触控区 20dp、字体裁切）在**可访问性**上比批次 1 更「硬」，但它们只影响少数用户的使用质量，而批次 1 影响全部用户的使用可能性。所以批次 1 在前。

| # | 风险 | 触发条件 | 影响 | 缓解 |

## 4. 第二部分：合规性评估

### 4.1 适用规范

| 规范 | 与本项目的关系 |
| --- | --- |
| 工信部信管〔2023〕105 号《关于开展移动互联网应用程序备案工作的通知》 | App 备案义务；从事互联网信息服务即适用，与是否上架应用商店无关 |
| 《移动互联网应用程序信息服务管理规定》 | 分发渠道（含官网 / GitHub）同样受约束 |
| 《个人信息保护法》 | `deviceId` + 跳过记录上报属个人信息处理，需告知同意 |
| 《反不正当竞争法》第二条 | 干扰他人广告业务的定性依据 |
| Google Play 开发者政策（无障碍 API 条款） | 仅影响出海；明令禁止将无障碍用于非无障碍目的 |

### 4.2 逐项结论

| # | 项 | 现状 | 风险 | 处置 |
| --- | --- | --- | --- | --- |
| C1 | **App 备案** | 未备案，全仓无备案号 | **高（法定强制）** | 批次 0.3。需主体实名 + 域名 ICP + 包名与 SDK 清单；审核约 20 工作日 |
| C2 | **隐私政策** | 不存在 | **高** | 批次 0.1/0.2。须覆盖：收集什么（`deviceId`、跳过记录）、存哪（自建服务器）、能否关闭（纯本地模式） |
| C3 | **个人信息告知同意** | 无同意流程，上报默认开启 | **高** | 批次 0.2。首启告知 + 可拒绝；拒绝后纯本地仍完整可用 |
| C4 | **无障碍用途说明** | 引导页未说明用途边界 | 中 | 批次 0.5。显式写明「只点已有按钮、不读内容、不传界面数据」 |
| C5 | **反不正当竞争** | 只点 UI 已有按钮、不上架商店、有免责声明 | 中（L1）/ 高（L2+） | 维持 L1 边界；L2/L3 过 Phase 0 前不实现。**注意**：项目文档中「吸收李跳跳不正当竞争诉讼先例」的表述需修正——公开信息显示李跳跳是 2023-08 收到律师函后停更，**未见生效判决**，写成「诉讼先例」会高估既有判例的确定性 |
| C6 | **软件著作权** | 无 | 低（但建议） | 备案与维权都需要；成本低，建议补 |
| C7 | **开源许可证** | GPL-3.0 | 低 | 已声明；注意 GPL 与「不上架商店」不冲突，但与未来闭源商业化冲突 |

### 4.3 合规结论

**可以继续开发与自用分发，但不具备公开、规模化分发条件。**

三条硬缺口（C1/C2/C3）都是「不做就违法」而非「做了更好」。其中 C1 周期最长，是唯一会阻塞其他一切的项——它决定「能不能合法地把 APK 给陌生人」。

C5 需要特别说明：L1 现状（只点已有按钮）在司法实践中争议较小，但**一旦做 L2 DNS 拦截，性质从「帮用户点按钮」变成「拦截他人广告投放」**，这是李跳跳收到律师函的直接原因类型。这也是本文把 L2/L3 排除在改造范围外的核心理由。

## 5. 第三部分：市场定位与需求匹配

### 5.1 竞品格局

| 产品 | 形态 | 规则分发 | 对本项目的含义 |
| --- | --- | --- | --- |
| **GKD**（开源，活跃） | 无障碍 + 声明式规则 | **社区订阅**，覆盖数百款应用、上千规则组 | 已经解决了「规则覆盖」这个最难的问题，且开源免费 |
| 李跳跳 | 无障碍，单机 | 内置规则 | 2023-08 律师函后停更，证明合规风险真实存在 |
| 厂商系统能力 | ROM 内置「关闭系统工具广告」 | 系统级 | 覆盖自家应用，不覆盖第三方 |
| AdGuard 等 | VPN / DNS | 域名规则 | 与本项目 L2 规划重叠，但成熟度与合规姿态更稳 |

**结论**：在「跳广告」这个具体功能上，GKD 已经占据了开源免费生态的位置，且它的护城河正是本项目最缺的那一环——规则覆盖与订阅分发。

### 5.2 需求真实性

需求是真实的，但要分层看：

| 需求层次 | 是否真实 | 说明 |
| --- | --- | --- |
| 讨厌开屏广告 | **真实且普遍** | 无需论证 |
| 愿意为去掉广告做额外操作 | **真实但门槛敏感** | 愿意装 App；但「去系统设置深层开无障碍 + 看厂商恐吓弹窗」这一步会筛掉大量普通用户 |
| 愿意自己配服务器 / 抄密钥 | **不真实（对大众）** | 这是开发者行为，不是用户行为 |
| 愿意自己维护规则 | **不真实（对大众）** | 同上 |

### 5.3 交付形态与使用场景的三处错配

这是本文最重要的判断，逐条给证据：

| # | 错配 | 大众用户的实际场景 | 当前设计 | 证据 |
| --- | --- | --- | --- | --- |
| M1 | **规则覆盖** | 装了就要能跳我常用的那 10 个 App | 规则库为空，需手动加关键词 | `RulesRepository.kt:29`、`server/seed/rules.json` |
| M2 | **配置成本** | 装完开个权限就完事 | 需填服务器地址 + HMAC 密钥 + 证书 pin | `Prefs.kt:53`、`SyncClient.kt` fail-closed |
| M3 | **效果可见性** | 跳没跳过要能立刻感知 | 规则空时不点任何东西，且无任何提示 | `HomeScreen.kt` 无空态分支 |

三处错配叠加的结果：**普通用户装完 App 后，得到的是「一个什么都不做的 App」**，而且不知道原因。

### 5.4 结论与定位建议

**结论：当前功能设计的方向符合大众需求，但产品形态只服务技术型用户。项目处于「自建自用的工程样板」状态，尚未进入「面向大众的产品」状态。**

这个判断不是否定——工程化、安全设计、契约测试的水准都支持它成为一个好产品。但它现在缺的不是代码质量，是**产品闭环**。

两条路，必须选一条，不能停在中间：

| 路径 | 做法 | 代价 | 适合 |
| --- | --- | --- | --- |
| **A. 转向大众** | 批次 1 全做（内置规则 + 订阅 + 零配置）+ 批次 0 合规三件套 | 备案与规则维护是长期成本；要与 GKD 正面竞争 | 想做成有用户量的产品 |
| **B. 收敛为极客工具** | 明确「自建自用」定位，README 与引导页如实说明需自配规则与服务端；放弃大众叙事 | 用户量上限极低，但合规压力最小 | 想保持技术探索性质 |

**建议选 A，但把「与 GKD 正面竞争」从目标里去掉。** 理由：GKD 的订阅生态已经赢了规则覆盖这一局，本项目不可能在「规则数量」上追平。可行的差异化只有两条——**隐私姿态**（纯本地优先、上报可选、代码可审计）与**工程可靠性**（契约测试、幂等上报、fail-closed 验签）。这两条恰好是本项目已经具备的，也是 GKD 这类社区项目较难保证的。

换句话说：不要做「另一个 GKD」，做「最可信的那个」。

## 8. 未采纳方案及理由

| 方案 | 不采纳理由 |
| --- | --- |
| 直接内置 GKD 的规则格式并复用其订阅源 | 格式与语义不同（GKD 用声明式 `json5` 规则组，本项目是选择器 + 关键词 + viewId 三通道）；直接兼容等于放弃自己的引擎设计，且规则语义无法一一映射 |
| 内置全部规则而非 Top 30 | 误点风险随规则数量线性上升，而验收成本同样线性上升；先做 Top 30 并逐条真机验收，再扩 |
| 用第三方崩溃 SDK（Bugly / Sentry） | 引入额外 SDK 会扩大备案的 SDK 清单与隐私披露范围；本项目规模用「本地环形缓冲 + 手动导出」足够 |
| 把服务器配置彻底删除 | 自建服务器是「隐私优先」定位的支撑（数据存自己的机器），降为可选但不删除 |
| 一次性硬性要求用户同意隐私政策才能使用 | 纯本地功能不涉及个人信息处理，强制同意会损害「隐私优先」的定位；应允许「拒绝上报但继续本地使用」 |
| 在批次 1 同时重构 UI | 功能回归与视觉回归混在一起无法归因（见 §3.4 R8） |
